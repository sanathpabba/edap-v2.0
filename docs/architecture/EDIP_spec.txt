======================================================================
1. PURPOSE OF THIS FILE
======================================================================

This file is the implementation context for Claude/Claude Code.

Treat this document as the baseline architectural and engineering specification for the EDIP project. The goal is to build a demonstrable end-to-end Enterprise Data Intelligence Platform that modernizes a legacy report-centric Capital Markets data environment into a governed, metadata-driven Lakehouse.

The project must demonstrate:

- Multiple heterogeneous source-system patterns.
- Orchestrated ingestion into a Landing area.
- Medallion-style processing using Landing, Bronze, Silver, Gold, and Platinum layers.
- Canonical Data Modeling in Silver.
- Reusable business data products in Gold.
- Consumer-specific serving and delivery in Platinum.
- Unity Catalog governance.
- Metadata-driven processing.
- Data catalog and lineage.
- DQX-based data quality controls at Bronze and Silver.
- Monitoring, observability, alerting, and remediation.
- Identity and access controls.
- Audit logging.
- Reference-data management.
- Scheduled, event-driven, and streaming pipelines.
- Cost/usage monitoring.
- Deployment and source-control practices.
- Multiple consumption mechanisms including Databricks dashboards, Power BI, cloud database publishing, and file/email delivery.

This is an academic prototype, not a production bank implementation. All data, schemas, source systems, mappings, and business examples must remain synthetic, generalized, and non-confidential.

Do not fabricate implementation results, performance improvements, cost savings, accuracy percentages, or business metrics. Only report measurements that are actually produced by the prototype.

SOURCE 2 — FILE-BASED SOURCE
Technology:
Azure Blob Storage / ADLS Gen2 or equivalent cloud object storage.

Purpose:
Daily position extract.

File pattern:

positions_YYYYMMDD.csv

Example:

positions_20261119.csv

Representative attributes:

- position_id
- portfolio_id
- instrument_id
- position_date
- quantity
- average_cost
- market_value
- currency
- source_system

Preferred inbound pattern:

Required demo scenarios:

B. Bad file containing deliberately introduced data-quality issues

Examples of controlled bad data:

- duplicate position_id

-> reprocessing

SOURCE 3 — STREAMING SOURCE
Technology:
Azure Event Hubs with Kafka-compatible interface, or Kafka if practical.

Purpose:
Trade lifecycle / trade execution events.

Representative event payload:

{
  "event_id": "EVT100023",
  "trade_id": "TRD100045",
  "instrument_id": "AAPL",
  "portfolio_id": "PF001",
  "counterparty_id": "CP012",
  "trade_type": "BUY",
  "quantity": 500,
  "price": 275.45,
  "currency": "USD",
  "event_type": "TRADE_EXECUTED",
  "event_timestamp": "2026-11-19T18:15:30Z"
}

Representative event types:

- TRADE_EXECUTED
- TRADE_AMENDED
- TRADE_CANCELLED
- TRADE_SETTLED

Primary ingestion pattern:
Continuous Structured Streaming.

Required concepts:

- event_id
- event_timestamp
- ingestion timestamp
- checkpointing
- duplicate event handling
- out-of-order events
- late-arriving events
- malformed/invalid events
- stream-to-Bronze persistence

Conceptual relationship:
Azure SQL trades represent current/system-of-record state.
Event Hub/Kafka represents business lifecycle events.

Optional validation:
Compare stream-derived state/event history with current trade state in Azure SQL.

Technology:
Public REST API.

Preferred business use:
FX / market reference rates.

Recommended API:
A public FX API requiring no sensitive credentials where possible.

Representative attributes:

- rate_date
- base_currency
- quote_currency
- exchange_rate
- source

Primary ingestion pattern:
Scheduled REST API pull.

Required concepts:

- API status validation
- ingestion timestamp
- stale-data handling
- optional pagination if available
- API response persistence into Landing/Bronze

Business use:

7. LANDING LAYER
======================================================================

Purpose:
Temporary receipt/staging zone for source data before formal table ingestion.

Landing is not the main business data model.

Preferred storage:
Unity Catalog external volume or governed cloud location.

Landing should preserve native or near-native source representations.

Examples:

- database extracts
- CSV files
- API JSON responses
- streaming micro-batch/event payload files if needed

Typical Landing metadata:

- source_system
- source_object
- received_timestamp
- source_filename/object
- batch_id
- run_id
- checksum if useful
- arrival status
- schema/version reference

Retention:
Potentially shorter than Bronze.

======================================================================
8. BRONZE LAYER
======================================================================

Purpose:
Immutable or minimally transformed, source-aligned data stored as Delta tables.

Preferred storage/governance:
Unity Catalog managed Delta tables wherever available.

Bronze must preserve replayability and source traceability.

Standard Bronze technical metadata should be added consistently.

Recommended metadata columns:

- _source_system
- _source_object
- _source_file_name
- _ingestion_timestamp
- _batch_id
- _run_id
- _record_source
- _schema_version
- _load_type
- _ingestion_status
- _record_hash

Not every field must be populated for every source, but naming conventions should be standardized.

Bronze should avoid heavy business transformations.

======================================================================
9. DQX AT BRONZE
======================================================================

Use the Databricks Labs DQX framework for Bronze technical/data-ingestion quality checks.

Bronze DQ question:
"Did we receive technically valid data?"

Representative Bronze checks:

- required source fields exist
- mandatory identifiers are non-null
- schema is readable
- expected data types can be interpreted
- timestamps parse correctly
- numeric fields are parseable
- duplicate source/event identifier detection
- malformed record handling
- unexpected schema change
- file/source freshness where relevant

Bronze should preserve source data wherever possible.

Preferred DQ outcomes:

- valid Bronze records
- marked invalid records where appropriate
- quarantine table/location for failed records
- DQ metrics
- DQ rule execution results
- alertable DQ summary

Avoid unnecessarily discarding source records.

-> multiple reusable consumers
