# Pipelines: asset classes, layers, Routine and Adhoc

```
pipelines/
  Common/        landing | bronze | silver | gold     shared: all landing, instrument master, portfolios, accounts, counterparties, FX rates, FX dimension
  Equities/      bronze | silver | gold               EQUITY + DERIVATIVE (equity options); also receives rows whose instrument no asset class knows
  FixedIncome/   bronze | silver | gold               BOND
  FX/            bronze | silver | gold               FX
  Commodities/   bronze | silver | gold               COMMODITY
      each layer:  Routine/  NN_<step>.py   scheduled incremental run
                   Adhoc/    NN_<step>.py   on demand: initial load, backfill, replay, rebuild, what-if
```
`definitions/asset_classes/<x>.yml` says what each pipeline covers (security types, items per layer). Change the routing there, not in code.

## One file = one framework function
Every step file is a few lines: `steps.<function>(ctx)`. The order of the numbered files is the pipeline; `pipelines/run.py` runs them in order
for each item of the layer (a table, entity or product). State (spec, DataFrame, counts) travels in the `PipelineContext`.
The tree is generated by `tools/generate_pipelines.py` from one step table, so Routine and Adhoc always have the same sequence (checked by the validator).

| Layer | Steps (8-10) | Functions in |
|---|---|---|
| landing (8) | init_context, read_source_yaml, resolve_extract_window, acquire_data, write_landing_files, register_landing_batch, advance_watermark, audit_log | `pipeline/landing_steps.py` |
| bronze (10) | init_context, read_source_yaml, resolve_scope, read_landing, shape_columns, route_to_asset_class, add_meta_properties, write_bronze, apply_governance, run_dq_and_audit | `pipeline/bronze_steps.py` |
| silver (10) | init_context, read_mapping_yaml, load_reference_data, read_bronze_increment, apply_canonical_mapping, deduplicate, apply_lookups, run_dq_silver, add_meta_properties, merge_and_finalize | `pipeline/silver_steps.py` |
| gold (9) | init_context, read_product_yaml, resolve_parameters, check_upstream, compose_sql, build_and_write, apply_documentation, run_expectations, audit_log | `pipeline/gold_steps.py` |

## Routine vs Adhoc (same steps, different behaviour inside the function)
| | Routine (scheduled) | Adhoc (on demand) |
|---|---|---|
| Landing | SQL: watermark delta; FX: today's rates; files: new files; events: drain | SQL: `--from-ts` or full re-extract; FX: history; files: `--rescan`; events: replay from earliest |
| Bronze | Auto Loader stream, incremental by file | batch read of a window; replayed landing batches are deleted then re-appended (no duplicates) |
| Silver | Bronze rows since the Silver watermark | since `--from-ts` or full rebuild; MERGE is idempotent; watermark only moves forward |
| Gold | YAML parameters | `--param name=value` overrides (what-if, e.g. a different large-exposure threshold) |

## How asset classes share the data
- Landing is source-level (Common): one extract per source table, whatever the asset class.
- **Common bronze** keeps the shared tables raw: instrument master, portfolios, accounts, counterparties, FX rates.
- **Asset-class bronze** (trades, positions, events) keeps only its rows: the row's instrument is looked up in the instrument master and its security type decides the asset class
  (`route_to_asset_class`). Rows whose instrument is unknown to every class go to Equities (`receives_unresolved`), so DQ quarantines them there rather than losing them.
- **Silver**: asset-class instrument/trade/position/trade_event; Common portfolio/account/counterparty/market_data. **Gold**: four products per asset class; the FX dimension is in Common.
- Table names: `edap.<layer>.<prefix>_<name>` (e.g. `edap.bronze.fixed_income_sql_trades`, `edap.silver.fx_trade`, `edap.gold.commodities_pnl_finance`).

## Run
```bash
python pipelines/run.py --asset-class ALL --layer landing --mode Routine       # Common only
python pipelines/run.py --asset-class ALL --layer bronze  --mode Routine       # Common first, then every asset class
python pipelines/run.py --asset-class Equities --layer silver --mode Adhoc --item trade --from-ts 2026-11-17
python pipelines/run.py --asset-class FX --layer gold --mode Adhoc --item regulatory_reporting --param large_exposure_threshold_usd=1000000
python pipelines/run.py --asset-class Equities --layer bronze --mode Routine --steps 1-5 --dry-run     # print the plan, no Spark
```
Jobs (`deployment/jobs.yml`, generated): daily routine (Common then each asset class), positions on file arrival, events drain every 15 minutes, one parameterised Adhoc job.

## Known limits (to confirm at first run)
- Per-asset-class Gold products are partial views for cross-asset questions: a counterparty's total exposure (regulatory) needs a cross-asset Consumption view over the four tables (not built yet).
- All step bodies are unrun on Databricks; the offline validator and the 37 unit tests check structure, wiring and SQL composition only.
